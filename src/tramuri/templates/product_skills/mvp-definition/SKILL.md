## When to use
Shape a first real product increment after the problem and target user are
understood well enough to make scope choices.

## When not to use
Do not use for a feasibility-only proof of concept or when a defined product
already needs only a narrow prioritization decision.

## Inputs
Problem and value hypotheses, target user, key risks, user journey and constraints.

## Process
Select the smallest coherent scope that can deliver the intended outcome and
test the riskiest assumptions. Identify dependencies, critical path, exclusions
and a learning loop.

## Output contract
Return an MVP boundary, included and excluded capabilities, critical path,
acceptance signals, risks and unresolved validation.

## Quality checklist
- [ ] Scope supports one coherent user outcome.
- [ ] Each included capability has a rationale.
- [ ] Acceptance signals are observable and unvalidated where appropriate.
- [ ] No unrelated breadth is added to make the plan look complete.
